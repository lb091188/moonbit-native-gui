# MNG 开发体验与发布构建隔离架构建议

**架构决策与实施建议**  
版本：1.1（补充 Debug / Release 一致性约束）  
日期：2026-11-26  
适用项目：`moonbit-native-gui` / MNG 工具链

---

## 1. 目标与核心决策

本文整理关于模板、样式和 MoonBit 脚本热更新的架构讨论，并明确一个关键前提：**热更新属于开发体验（DX），不是发布后应用的运行时能力。**

项目应该持续增强开发阶段的动态能力，而不是为了照顾发布版性能而限制热更新。与之对应，`mng package` 应在构建阶段生成纯生产产物，将 Dev Runtime、热更新协议、表达式 VM、Hot Script VM、开发服务器等开发专用能力排除在发布依赖图之外。

### 1.1 核心架构决策

1. **开发能力持续增强。** 模板热更新、样式热更新、节点 Diff、表达式求值以及 MoonBit 脚本热替换都属于 Dev Runtime 的职责，可以独立演进。
2. **发布产物不携带热更新运行时。** Release 不应通过 `is_dev = false` 在运行时关闭热更新，而应通过独立构建入口和依赖图隔离，使 Dev Runtime 根本不进入最终链接产物。
3. **一份 `.mng`，两种编译输出。** Dev 构建输出可动态替换的 IR、样式数据、表达式/脚本描述和调试元数据；Release 构建输出普通 MoonBit AOT 代码及静态样式定义。
4. **共享 UI 语义，不复制 UI 实现。** 两种构建共享组件、布局、事件和渲染语义；区别在于编译输出和开发期的应用机制，不应维护两套控件系统或两套渲染器。Debug 初始页面也必须走生产 AOT 执行路径，VM 只负责开发期间的动态替换，不能成为 Debug 的默认执行引擎。
5. **生产运行时只保留产品本身需要的能力。** 生产样式注册、布局、事件、渲染和业务逻辑必须保留；动态解析、替换、补丁应用、开发通信等能力应剔除。

### 1.2 “零热更新负担”的准确含义

这里的目标是：发布应用不包含热更新专用代码，不启动热更新服务，不注册热更新状态，不解释热更新表达式，也不为热更新保留额外常驻内存或 CPU 路径。

这不等于发布版完全没有模板或样式运行时。生产应用仍然需要正常的组件、布局、样式应用和渲染代码。需要剔除的是**热更新机制**，不是 GUI 正常运行所需的基础设施。

## 2. 总体架构：Dev Runtime 与 Production Runtime 分离

### 2.1 开发构建

开发构建由正常 AOT 应用代码与 Dev Runtime 共同组成。Dev Runtime 为开发过程提供：

- 文件监听、开发服务器和热更新通信；
- 模板 IR 生成、校验、补丁应用和节点 Diff/Reconcile；
- 样式数据解析、替换、删除、命名空间和原子提交；
- 表达式 AST/字节码执行；
- Hot Script 的解析、类型检查、执行和函数体替换；
- 热更新错误报告、源码位置映射、调试信息和运行时检查。

开发进程中的初始页面、普通应用逻辑和正常事件回调仍由 AOT 编译代码提供。只有开发者实际触发热更新后，需要动态替换的模板/样式/脚本部分，才由 Dev Runtime 接管或应用补丁。这样 Debug 的初始运行结果与 Release 尽可能来自同一条 AOT 路径。

### 2.2 发布构建

发布构建只包含：

- Production GUI Runtime：组件、布局、事件、渲染、生产样式应用等；
- 由 `.mng` 生成的普通 MoonBit AOT 代码；
- 编译期确定的模板结构和静态样式定义；
- 应用正常需要的业务代码、资源和平台适配层。

发布构建不应包含：

- `mngdev`；
- Dev Socket / WebSocket / 热更新服务器；
- 文件监听与开发进程管理；
- Template IR Patch Applier；
- 仅用于热更新的表达式 VM 和 Hot Script VM；
- 动态样式表替换与开发期样式数据加载器；
- 开发调试注册表、热更新历史和开发诊断服务。

## 3. 同一 `.mng` 的双输出模型

`.mng` 是唯一的 UI 源描述。编译器前端负责解析、语义分析、类型检查和统一校验；后端根据构建目标生成不同产物。

| 输入内容 | Dev 输出 | Release 输出 |
|---|---|---|
| `<template>` | 完整模板 IR、节点身份、动态绑定描述 | 组件构造与更新所需的 AOT MoonBit 代码 |
| `<style>` | 可替换的 StyleSheet 数据、类名/状态元数据 | 静态样式定义和生产样式注册代码 |
| `<script>` | 热更新脚本描述、函数签名、必要的 AOT Host 函数注册信息 | 普通 MoonBit AOT 代码 |
| 表达式 | AST 或字节码、依赖信息、源码映射 | 编译为原生表达式/闭包，不依赖表达式 VM |
| 事件回调 | 可替换的逻辑函数标识与调用绑定 | 直接绑定 AOT 函数或闭包 |

### 3.1 建议的编译流水线

```text
                 .mng 源文件
                      |
             MNG Compiler Frontend
       解析 / 类型检查 / 组件校验 / 语义分析
                      |
             统一中间语义模型
                      |
             +--------+--------+
             |                 |
          Dev Backend      Release Backend
             |                 |
        Template IR         AOT MoonBit
        Style Data          Static Styles
        Expr AST/Bytecode   Native Bindings
        Hot Script Data     Normal App Code
        Debug Metadata      Production Assets
             |                 |
        Dev Runtime       Production Runtime
             |                 |
      开发期间动态更新       发布应用
```

这条流水线的关键不是维护两个 UI 实现，而是让同一套语义分析结果由两个后端分别输出动态开发产物和原生发布代码。Dev 和 Release 可以有不同的产物格式，但不能有不同的语法解释、类型规则、组件属性含义、布局语义或事件语义。

### 3.2 编译器前端和后端的职责

**编译器前端共享：** 标签与属性合法性、组件描述、表达式语义、样式属性定义、事件类型、错误定位等。尽量避免 Dev 和 Release 各自实现一套互不一致的语法规则。

**Dev Backend 专属：** 生成可动态替换的模板/样式/脚本数据、稳定节点 ID、依赖图、调试元数据和补丁协议所需信息。

**Release Backend 专属：** 生成可由 MoonBit 正常 AOT 编译的代码，静态固化模板结构和样式定义，直接使用生产 API。


### 3.3 单一语义源：防止 Debug 与 Release 结果漂移

双输出不等于双重语义。最重要的约束是：**同一份 `.mng`、同一组输入状态和同一套平台环境，在没有热更新介入时，Debug 与 Release 必须表现一致。**

建议采用“统一前端 + 统一语义模型 + 两个后端”的结构：

- **统一前端：** 解析、名称解析、类型检查、组件/属性校验、表达式语义和样式属性定义只实现一套。
- **统一语义模型：** 在后端分流前，形成明确、可测试的 Semantic IR；它描述 UI 应该是什么，而不是描述某个后端如何执行。
- **Dev Backend：** 额外生成热更新所需的节点 ID、依赖信息、AST/字节码、源码映射和补丁元数据。
- **Release Backend：** 将同一语义模型转换为普通 MoonBit AOT 代码、静态样式和原生绑定。
- **共享 Production GUI Runtime：** 组件、布局、事件、状态和渲染实现由两种模式共同使用，不为 Debug 另写一套控件或布局实现。

特别要避免：Dev 使用解释器定义一套表达式语义，而 Release Backend 又独立生成另一套表达式语义。两者应由同一语义分析和类型规则约束，并通过一致性测试验证。

#### Debug 的初始页面必须是 AOT

Debug 启动时，页面应由 Release 同源的 AOT 生成代码构建。Dev Runtime 在旁边提供监听和更新服务。收到更新后，Dev Runtime 才将变化后的 IR/样式/脚本应用到当前页面。

因此，VM 是“热更新执行能力”，不是“Debug 页面运行引擎”。这可以显著降低 Debug 与 Release 在初始运行行为上的差异。

#### 热更新能力必须能落到 Release 编译语义

热更新可以比 Release 编译拥有更灵活的增量应用方式，但不能接受 Release 永远无法理解的应用语义。对最终需要发布的修改，必须能够通过完整 Release 编译与校验。

如果某种 Hot Script 语法只允许在开发期执行，不能转换成生产 AOT 代码，则应明确标记为开发专用，并在 `mng package` 阶段报错或要求开发者替换；不得静默忽略、自动降级或生成行为不同的代码。

#### 保持一致的内容与允许不同的内容

| 项目 | Debug / Release 要求 |
|---|---|
| `.mng` 语法与解析 | 完全一致 |
| 名称解析、类型检查 | 完全一致 |
| 组件、属性和事件语义 | 完全一致 |
| 样式属性定义与优先级 | 完全一致 |
| 布局算法、约束和测量规则 | 完全一致 |
| Store / 响应式状态语义 | 完全一致 |
| 表达式语义与错误规则 | 完全一致 |
| 生产组件、布局和渲染实现 | 共用 |
| 文件监听、热更新通信 | 仅 Debug |
| IR Patch Applier、热更新历史 | 仅 Debug |
| VM / Hot Script Runtime | 仅 Debug |
| 调试日志、源码映射和诊断 UI | 可仅 Debug |
| 优化级别、断言和诊断信息 | 可以不同，但不得改变正确性 |

## 4. VM 的定位：增强开发体验，不进入发布包

当前项目中的表达式求值实现属于受限表达式解释器/小型 VM，并不是完整的 MoonBit 解释器。其存在不应成为发布应用的负担，因为它应该属于 Dev Runtime。

建议未来的开发期执行能力分为两个层次：

### 4.1 Expression Runtime

服务于模板中的表达式、动态文本、动态属性、条件和轻量计算。后续可从现有 AST 求值器增强为经过类型检查的字节码执行器，并加入表达式依赖追踪、常量折叠、执行预算和缓存。

### 4.2 Hot Script Runtime

服务于开发期间需要替换函数体的 MoonBit 脚本。它可以逐步扩展语法覆盖范围、控制流、局部变量、集合、模式匹配和函数调用，并允许调用稳定的 AOT Host 函数，例如文件、网络、系统能力和复杂业务服务。

完整 MoonBit 语义的覆盖范围需要通过分阶段设计和兼容性测试来确定，尤其需要单独处理 FFI、异步、泛型、Trait、运行时类型和外部资源生命周期。这个复杂度属于开发工具链的工程问题，不应反过来限制模板/样式热更新，也不应进入生产运行时。

### 4.3 VM 性能边界

开发模式可以接受为动态执行付出的额外成本，但仍然需要保证开发体验流畅。建议采用：

- 表达式在更新时解析/编译一次，后续复用 AST 或字节码；
- Store 变化时只重新计算受影响的表达式，而不是每帧扫描全部表达式；
- 将 UI 依赖计算与绘制过程分开；
- 对指令数、递归深度、内存和单次执行时间设置预算；
- 高频或重计算逻辑可委托给 AOT Host 函数；
- 提供 VM 与 AOT 的基准测试，但不把 VM 放入 Release 的性能关键路径。

## 5. 模块边界与现有代码映射

以下映射基于 `moonbit-native-gui` 仓库 `dev` 分支在 2026-11-25 左右的代码审查结果。它是架构归属建议，不代替后续对 MoonBit 实际包依赖图、链接结果和构建产物的验证。

| 现有路径/模块 | 建议归属 | 说明 |
|---|---|---|
| `tools/native-gui-tools/mngkit` | Build-time Tooling | `.mng` 解析、编译、IR 生成等工具，不进入应用运行时 |
| `gui/mngdev/mng_dev.mbt` | Dev Runtime | 注册表、补丁接收/应用、开发期页面更新 |
| `gui/mngdev/mng_eval.mbt` | Dev Runtime | 表达式 AST 求值能力 |
| `gui/mngdev/mng_style_data.mbt` | Dev Runtime | 动态样式数据解析和应用适配 |
| `gui/style/class_registry.mbt` | 按职责拆分 | 生产静态样式查询/应用能力保留；动态替换、清理和 Dev 管理能力单独隔离 |
| GUI 组件、布局、事件、绘制核心 | Production Runtime | Dev 与 Release 共用的产品运行能力 |

### 5.1 不能只靠目录名称隔离

把代码放在 `gui/mngdev` 目录下是有帮助的，但目录分隔本身不能证明发布产物中没有这些代码。必须检查真实包依赖图和链接结果。

建议建立单向依赖规则：

```text
Build-time Tooling  --->  Dev Runtime  --->  Shared GUI Core
          |                                  ^
          +----------> Release Backend ------+
                                             |
Production App  ----------------> Production GUI Runtime
```

更准确地说，生产应用应依赖 Production GUI Runtime 和 Release 生成代码；它不应有任何路径依赖 Dev Runtime。共享 GUI Core 可以被 Dev Runtime 和 Production Runtime 使用，但不能反向依赖 Dev 专属实现。

## 6. `mng package` 的目标行为

建议将开发与发布命令的语义清晰化：

```bash
# 开发运行：连接完整 Dev Runtime
mng dev

# 生产打包：生成 AOT 产物，不包含 Dev Runtime
mng package
```

以上是目标命令语义；若当前 CLI 名称或参数不同，应按现有工具链兼容性调整，不应误认为所有参数现已实现。

`mng package` 应至少完成：

1. 扫描并编译所有 `.mng` 文件，执行完整语法、类型和组件校验；
2. 使用 Release Backend 生成生产用 MoonBit 代码和静态样式定义；
3. 以独立 Release 入口构建应用，不引用 `mngdev`；
4. 不引入 Dev Socket、文件监听、IR Patch Applier、表达式 VM、Hot Script VM 等模块；
5. 只复制生产应用实际需要的资源；
6. 在打包结束时执行依赖图和产物检查；
7. 运行至少一组 Release 冒烟测试，确认模板、样式、输入、事件和渲染功能正常。

不建议把下面这种运行时分支作为主要隔离手段：

```moonbit
if is_dev {
  // hot reload implementation
} else {
  // normal production execution
}
```

即使编译器可能执行常量折叠或死代码消除，也不应把“希望链接器剔除”作为架构保证。优先使用独立包、独立构建入口和清楚的依赖根；编译期条件和死代码消除只能作为辅助优化。

## 7. 样式系统的边界

样式需要区分“生产时应用样式”和“开发时动态替换样式”。

**生产必须保留：** Style 数据结构、布局/绘制实际读取的样式字段、静态样式注册和查询、组件状态对应的正常样式应用。

**开发专属：** CSS-like 源解析后的动态数据加载、类表快照替换、热更新删除旧类、页面/模块命名空间、补丁版本管理和更新事务。

因此，不应为了剔除热更新而删除 `class_registry` 中生产渲染仍然使用的能力。应当拆分稳定的生产接口和开发期管理接口。

## 8. 发布隔离的自动化验收标准

发布隔离不能只依靠约定，应成为 `mng package` 和 CI 的硬性检查。与此同时，CI 必须验证双后端的行为一致性；只证明 Dev Runtime 被剔除还不够。

| 验收项 | 通过标准 | 验证方法 |
|---|---|---|
| 依赖图 | Release 依赖闭包不包含 `gui/mngdev` | 包依赖图静态检查 |
| Dev 符号 | Release 不引用 `mng_dev_apply`、表达式 VM 等 Dev 符号 | 符号/链接映射检查；符号剥离时以依赖图为主 |
| 通信能力 | Release 不启动 Dev Socket/热更新服务 | Release 冒烟测试、端口/进程检查 |
| 文件监听 | Release 不创建开发期文件监听器 | 依赖审计和运行时测试 |
| 动态解释器 | Release 不包含热更新 AST/字节码执行器 | 依赖图、构建清单和产物检查 |
| 静态样式 | Release 中正常样式定义可用 | 组件样式回归测试 |
| 模板功能 | Release 模板行为与 Dev 初始渲染一致 | 同一用例的 Dev/Release 行为对照 |
| 事件与状态 | 正常事件、Store 绑定、输入状态行为正确 | 自动化 GUI 测试 |
| 产物体积 | 记录 Dev/Release 产物差异并监控回归 | CI 产物尺寸报告 |

二进制字符串搜索可以作为辅助证据，但不能作为唯一证明：符号可能被剥离、内联或改名。依赖图和构建清单才是主要证据。


### 8.1 Debug / Release 行为一致性验收

建议建立专门的 **Parity Test Suite（双构建一致性测试集）**。每个关键 `.mng` fixture 使用同一份源文件、同一组初始状态、同一组输入事件和同一平台配置，分别运行 Debug AOT 初始页面与 Release 页面，再比较可观察结果。

| 测试类别 | 比较内容 | 建议断言 |
|---|---|---|
| Template Parity | 组件树、节点类型、父子关系 | 结构与节点语义一致 |
| Style Parity | 计算后的样式属性 | 属性值、状态优先级一致 |
| Layout Parity | 节点位置、尺寸、裁剪区域 | 在明确的浮点容差内一致 |
| Expression Parity | 动态文本、属性和条件结果 | 相同输入产生相同结果 |
| State Parity | Store 更新、订阅和批处理 | 状态变化顺序与最终值一致 |
| Event Parity | 点击、输入、焦点和事件传播 | 回调顺序及副作用一致 |
| Hot Reload Parity | 热更新后页面与重新完整编译页面 | 更新后的可观察行为一致 |

建议采用三层测试：

1. **语义级测试：** 对 Semantic IR、表达式求值结果、样式计算结果做单元测试。这一层速度快，能定位前端或后端语义漂移。
2. **运行时级测试：** 在相同 GUI Runtime 中分别加载 Debug AOT 和 Release AOT 生成的页面，比较节点树、布局、状态和事件结果。
3. **端到端测试：** 对关键页面执行相同交互并进行截图回归。截图用于补充发现视觉差异，不应成为唯一判据。

布局数值比较应定义容差，避免浮点误差导致无意义失败；但容差不能大到掩盖真实错位。截图测试应固定窗口尺寸、DPI、字体、主题、渲染后端和动画时刻，减少环境噪声。

CI 至少应包含以下门槛：

- 同一 `.mng` fixture 必须同时通过 Dev 与 Release 编译；
- 两个后端必须通过共享语义测试；
- Debug AOT 初始页面与 Release 页面必须通过关键行为对照；
- 热更新后的页面必须与该版本源代码重新完整 Release 编译后的结果对照；
- Release 产物仍须通过 Dev Runtime 依赖闭包检查。

## 9. 建议实施顺序

### 阶段 1：建立构建隔离基线

- 梳理现有 MoonBit 包依赖图，标出所有 Dev 专属模块；
- 确定 Production Runtime、Dev Runtime 和 Build-time Tooling 的包边界；
- 建立独立 Release 构建入口；
- 在 CI 中加入 Release 依赖闭包检查；
- 验证发布产物不包含现有 `mngdev` 代码。

**阶段完成标准：** 即使暂时不扩展热更新功能，也能证明 Release 不依赖当前 Dev Runtime。

### 阶段 2：实现 `.mng` 双输出

- 统一前端语义模型；
- 将 Dev Backend 与 Release Backend 分开；
- Release Backend 把模板生成成正常 AOT 代码；
- 将样式输出为静态生产定义；
- 用一致性测试确保 Dev 首次渲染与 Release 行为一致。

**阶段完成标准：** 同一份 `.mng` 可以生成 Dev 动态产物和 Release 原生产物，控件语义一致。

### 阶段 3：增强模板与样式热更新

- 补齐模板 IR 的组件、children、slot、循环和条件结构；
- 增加稳定节点 ID 与 keyed list 身份；
- 实现节点 Diff/Reconcile，减少整棵树替换；
- 样式使用可替换快照，支持新增、修改和删除；
- 样式和模板更新采用事务式提交，失败时保持旧界面和旧样式一致。

**阶段完成标准：** 模板和样式的更新范围不再被当前受限 IR 的支持边界意外限制；更新失败不会留下半提交状态。

### 阶段 4：增强 MoonBit 脚本热更新

- 明确热更新函数与普通 AOT 函数的身份、签名和状态绑定机制；
- 扩展表达式执行能力并引入经过类型检查的字节码；
- 逐步扩展 Hot Script 的语法和控制流；
- 支持函数体替换、调用关系更新和错误定位；
- 对 FFI、异步、泛型、Trait 和外部资源生命周期建立明确兼容策略；
- 通过回归测试对照正常 MoonBit 编译语义。

**阶段完成标准：** 开发期脚本热替换具备稳定、可诊断、可回滚的语义；所有动态脚本能力仍然只属于 Dev Runtime。

### 阶段 5：发布隔离持续守护

- 每次新增 Dev 功能时，必须同步更新 Release 依赖 denylist；
- CI 自动比较 Release 依赖闭包和产物尺寸；
- 将 Release 冒烟测试作为合并门槛；
- 防止共享模块通过反向依赖重新引入 Dev Runtime。

## 10. 风险与需要提前处理的问题

1. **共享模块边界不清。** 生产样式注册、状态绑定等能力容易与开发期动态替换逻辑混在一起。应按职责拆分 API，而不是粗暴删除整个模块。
2. **Dev/Release 语义漂移。** 两个后端如果独立实现语义，可能出现开发环境正常、发布版本行为不同。必须共享语义模型，并以 Parity Test Suite 作为 CI 门槛。
3. **脚本热替换的语言兼容性。** 完整 MoonBit 脚本动态执行不是简单扩展几个 AST 节点；需要定义 FFI、异步、类型表示和外部资源的边界。
4. **把 DCE 当作隔离保证。** 仅靠运行时布尔开关或链接器优化不够稳健，必须以依赖图隔离为主。
5. **把“零负担”误解为删掉生产能力。** 模板生成、样式应用和组件运行仍是产品功能；应只移除开发期动态更新能力。

## 11. 最终架构原则

> **Dev Runtime 可以复杂，Production Runtime 必须精简。**
>
> 开发期的热更新能力不应因为发布性能顾虑而被限制；发布期也不应为了支持开发热更新而携带额外的运行时代码。Debug 与 Release 可以有不同的构建产物和开发附加能力，但必须共享同一套 UI 语义、生产运行时和编译前端，并通过差分测试证明行为一致。

项目的优化目标是同时提高两个方向的上限：

- **开发阶段：** 尽可能完整、快速、可靠的模板、样式和 MoonBit 脚本热更新体验；
- **发布阶段：** 仅保留应用正常运行所需的 AOT 代码和生产 GUI Runtime，不包含热更新专用模块和执行路径。

这应成为 MNG 工具链、GUI Runtime 和 `mng package` 的长期架构约束。
