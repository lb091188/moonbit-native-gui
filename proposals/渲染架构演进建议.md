# native-gui GPU 渲染架构审查与演进建议

**审查对象：** `lb091188/moonbit-native-gui`  
**审查分支：** `dev`  
**审查基准 Commit：** `1be8de2afe4d08194c386d8799c71e36a0adf1f2`  
**审查日期：** 2026-11-26

---

# 1. 目标与最终结论

## 1.1 项目目标

native-gui 希望实现：

- MoonBit 负责业务逻辑、UI 状态、布局、事件和控件树。
- CPU 尽可能减少界面像素绘制工作。
- GPU 负责高效的图形绘制、图像处理、动画及窗口合成。
- 同一套控件代码支持软件光栅和硬件加速。
- 用户可以在运行时切换渲染模式。
- GPU 不可用时自动回退，不影响应用运行。
- Windows、Linux、macOS 保持统一的 UI 视觉语义。

## 1.2 核心架构决策

建议采用：

**统一 UI Core + 统一绘制语义 + 多个 Renderer + 独立 Present Backend。**

不要把 GPU 变成另一套 GUI。

也不要立即将现有 Painter 的所有方法改写成 GPU 专用实现。

建议把渲染分成两个独立问题：

1. 如何生成界面像素：CPU Raster 或 GPU Renderer。
2. 如何把画面呈现到窗口：CPU Present 或 GPU Present。

这两个维度应该可以独立组合。

## 1.3 最终推荐的三种运行模式

| 模式 | UI 绘制 | 窗口呈现 |
|---|---|---|
| Software | CPU 光栅 | CPU Present |
| GPU Composition | CPU 光栅 | GPU Present |
| GPU Rendering | GPU Renderer | GPU Present |

其中 GPU Composition 是目前已经实现的主要 GPU 路径。

GPU Rendering 是未来真正减少 CPU 绘制负担的目标。

# 2. 当前代码审查

## 2.1 Painter

文件：`gui/render/painter.mbt`

目前：

- `Painter` 持有 `Bitmap`。
- `Backend` 包含 `CairoBackend` 和 `PureBackend`。
- `Painter::new(bitmap)` 根据运行环境选择 Cairo 或纯 MoonBit Raster。
- 绘制操作直接修改 Bitmap。
- `Painter::end()` 结束当前后端会话。

这是一个 CPU 软件光栅 Painter。

优点：

- 接口统一。
- Cairo 与 Pure Raster 可以复用控件绘制逻辑。
- 软件光栅可以作为正确性参考实现。
- 不依赖 GPU。
- 无 GPU 环境也可以运行。

问题：

Painter 目前不是一个抽象的多后端绘制接口，而是一个绑定 Bitmap 的 CPU 绘制器。

不建议直接把它强行改成 GPU 对象。因为现有方法包含路径、裁剪、混合、渐变、图片、文本及大量状态管理，GPU 实现不只是替换几个函数。

建议保留它作为 Software Renderer 的实现。

## 2.2 RenderCtx

文件：`gui/render/render_ctx.mbt`

当前结构：

- `RenderCtx::Cpu(Painter)`
- `RenderCtx::Gpu(GpuCtx)`

同时存在 `GpuSink` trait。

目前 GpuSink 只提供：

- `draw_texture_rgba`
- `fill_rect`

这足以支持最小 GPU 内容绘制，但不足以替代完整 Painter。

另外，`gpu_backend_available()` 当前返回 false。

判断：

L2 的协议入口已经建立，但尚未成为普通控件的统一 GPU 绘制后端。

## 2.3 Widget

文件：`gui/widget/widget.mbt`

目前 Widget 有：

- `on_draw(Widget, Painter, Rect)`
- `on_render(Widget, RenderCtx, Rect)`

`paint_at()` 中的行为：

- 有 `on_render` 且 GPU Sink 已设置时走 GPU 分支。
- 否则 `on_render` 使用 CPU Painter。
- 没有 `on_render` 时使用 `on_draw`。

这是一个很好的兼容设计。

但它还存在一个需要后续解决的问题：

GPU 路径目前不继承 Painter 的完整变换能力。代码也明确注释了 GPU 档的 `on_render` 不处理 Painter 的 transform。

所以不能把现在的 RenderCtx 当作完整的 CPU/GPU 统一绘制抽象。

## 2.4 GPU Sink

文件：

- `gui/widget/gpu.mbt`
- `modules/gui-gpu/gpu/gpu.mbt`

目前 GPU Sink 使用进程级单槽：

`g_gpu_sink`

`GpuCanvas::install()` 将一个 GpuCanvas 安装为全局 Sink。

这对单个 GPU Demo 很方便，但不适合成为最终的多窗口 GUI Renderer 管理机制。

主要问题：

1. 所有窗口共享同一个 Sink。
2. Sink 与具体 GpuCanvas 绑定。
3. GpuCanvas 有自己的尺寸和生命周期。
4. 缺少每窗口 Renderer 的独立资源管理。
5. 没有形成完整的 Widget Tree GPU 合成器。

建议未来把 Renderer 放到每个 WindowHost 的窗口状态中，而不是使用进程级单槽。

## 2.5 WindowHost::paint_frame

文件：`gui/widget/app.mbt`

当前流程：

1. 读取窗口尺寸和 DPI。
2. 创建或复用 Bitmap。
3. 创建 Painter。
4. 执行布局。
5. 通过 Widget Tree 绘制。
6. flush 文本批。
7. 结束 Painter。
8. 调用 Window::present。

这说明目前普通 UI 的像素生成仍然在 CPU。

即使 L1 GPU Present 成功，CPU 仍然完成了前面的界面绘制工作。

这是整个架构目前最重要的性能边界。

## 2.6 L1 GPU Present

文件：`gui/win/stub.c`

当前流程：

1. CPU 将 Widget Tree 绘制到 Bitmap。
2. Bitmap 像素上传到 GPU Texture。
3. GPU 使用全屏 Quad 采样 Texture。
4. GPU 输出到 Swapchain。
5. Surface Present。

已经实现：

- wgpu-native 动态加载。
- Adapter / Device 探测。
- Windows、Linux、macOS 的窗口 Surface 路径。
- 每窗口 GPU Present 状态。
- 尺寸变化后的资源重配。
- 最小化和恢复处理。
- GPU 不可用时回退 CPU。
- 脏区纹理上传。
- GPU 故障后的窗口回退。

这部分已经有相当多的真实工程工作。

需要注意：

L1 GPU Present 并不代表普通控件已经由 GPU 绘制。

它的主要作用是 GPU 窗口呈现和合成。

## 2.7 GpuCanvas

文件：

- `modules/gui-gpu/gpu/gpu.mbt`
- `modules/gui-gpu/gpu/canvas.c`
- `modules/gui-gpu/gpu/frame.mbt`

GpuCanvas 已经具备：

- GPU 离屏目标。
- 纹理绘制。
- 矩形绘制。
- Shader。
- Vertex Buffer。
- Bind Group。
- Render Pipeline。
- Depth Attachment。
- 3D 帧生命周期。

但是 `finish()` 需要 GPU 读回 CPU Bytes。

这是一个面向离屏内容和应用自定义 GPU 绘制的接口，不应该作为未来普通 UI 每帧的最终呈现路径。

GpuCanvas 的读回成本和 L1 的 GPU Surface Present 是两件不同的事情，不要混为一谈。

# 3. 当前最重要的架构问题

## 3.1 CPU 绘制和 GPU 呈现仍然是两个阶段

目前：

Widget Tree → CPU Painter → Bitmap → GPU Texture → Surface

CPU 仍然需要绘制全部普通控件。

如果目标是释放 CPU 的像素计算能力，仅完成 L1 不够。

## 3.2 缺少独立的渲染模式配置

目前 L1 根据运行时探测自动尝试 GPU。

但还没有一个完整的用户 API，可以在运行时选择：

- 自动。
- 软件光栅。
- GPU 加速。

建议加入统一配置入口。

## 3.3 GPU Sink 不是窗口级 Renderer

目前 `g_gpu_sink` 是进程级状态。

未来应该按 WindowHost 管理：

- 每个窗口自己的 Renderer。
- 每个窗口自己的 GPU Surface。
- 每个窗口自己的 Render Target。
- 每个窗口自己的资源缓存。
- 每个窗口自己的呈现模式。

多窗口之间不应该共享一个有尺寸状态的 GpuCanvas。

## 3.4 GPU 绘制语义不完整

未来普通控件 GPU 化需要覆盖：

- 矩形。
- 路径。
- 圆角。
- 描边。
- 渐变。
- 图片。
- 文本。
- 裁剪。
- Transform。
- Opacity。
- Blend Mode。
- 阴影。
- 模糊。
- 图层。

不应只为现有两个 GpuSink 方法扩展几个控件，然后把它称为完整 GPU Renderer。

# 4. 推荐目标架构

建议：

```text
Application
    |
    v
WindowHost
    |
    +---- Widget Tree
    |
    +---- Layout Engine
    |
    +---- Event System
    |
    v
Render Manager
    |
    +---- Render Policy
    |
    +---- Software Renderer
    |        |
    |        +---- Cairo
    |        +---- Pure Raster
    |
    +---- GPU Renderer
    |        |
    |        +---- wgpu-native
    |        +---- GPU Texture
    |        +---- GPU Pipeline
    |        +---- GPU Composition
    |
    v
Present Backend
    |
    +---- CPU Present
    |
    +---- GPU Surface Present
    |
    v
Native Window
```

重要原则：

- Widget 不依赖具体 Renderer。
- Renderer 不负责业务状态。
- WindowHost 管理窗口级 Renderer。
- Present Backend 不应该负责控件绘制。
- GPU 资源和 CPU Bitmap 生命周期分离。

# 5. 运行时渲染模式切换

这是建议优先实现的功能。

## 5.1 对外 API

建议设计：

```moonbit
pub(all) enum RenderMode {
  Auto
  Software
  Hardware
}
```

应用：

```moonbit
app.set_render_mode(RenderMode::Auto)
```

也可以在运行时：

```moonbit
app.set_render_mode(RenderMode::Software)
app.set_render_mode(RenderMode::Hardware)
```

API 名称可以根据现有 App 和 WindowHost 的结构调整。

## 5.2 三种模式语义

### Auto

- 优先使用 GPU。
- GPU 不可用则使用软件光栅。
- GPU 设备丢失时自动回退。
- 保证应用尽可能继续运行。

### Software

- 禁止 GPU Present。
- 使用 CPU Raster。
- 使用 CPU Present。
- 用于兼容性测试、问题排查和性能基线。

### Hardware

- 优先使用 GPU。
- 初始化失败时应提供明确状态。
- 不允许把实际运行在 CPU 的情况误报为 GPU。
- 应用不能因为 GPU 故障而丢失业务状态。

建议内部再区分 HardwarePreferred 和 HardwareRequired：

- Preferred：GPU 优先，故障允许降级。
- Required：用于严格性能测试，不满足条件时报告失败。

## 5.3 切换流程

```text
请求切换模式
      |
      v
等待当前帧结束
      |
      v
初始化目标 Renderer
      |
      v
检查设备和 Surface
      |
      +---- 失败 ----> Auto 模式回退 CPU
      |
      v
准备目标后端资源
      |
      v
切换 Renderer
      |
      v
强制整窗重绘
      |
      v
释放旧后端专属资源
```

必须保留：

- Widget Tree。
- Store / Signal。
- 焦点。
- 滚动位置。
- 输入法状态。
- 业务对象。
- 窗口状态。

切换后端不能重建整个应用。

## 5.4 为什么应该按窗口切换

当前 `WindowHost::paint_frame()` 是逐窗口绘制。

因此推荐：

```text
WindowHost
  ├── RenderMode
  ├── Renderer
  ├── PresentBackend
  ├── GpuSurface
  └── ResourceCache
```

而不是让整个进程共用一个 GPU Sink。

这样未来多窗口可以：

- 窗口 A 使用 GPU。
- 窗口 B 使用软件光栅。
- 窗口 C 使用 Auto。

而不影响其他窗口。

# 6. CPU / GPU 双 Renderer 的演进方式

## 6.1 不要立即重写 Painter

现有 Painter 已经承载大量功能。

直接把 Painter 的每个方法改成 GPU API，会产生：

- 大量状态管理改动。
- GPU 命令提交问题。
- 文本兼容问题。
- 裁剪和变换语义问题。
- 旧控件兼容问题。
- 难以定位的视觉差异。

不建议一次性迁移。

## 6.2 建立统一绘制语义

建议未来引入 DrawList / DisplayList。

它不是另一套控件系统，而是控件绘制操作的中间表示。

例如：

```text
Widget Tree
    |
    v
DrawList
    |
    +---- FillRect
    +---- StrokeRect
    +---- DrawPath
    +---- DrawText
    +---- DrawImage
    +---- Clip
    +---- Transform
    +---- Opacity
    |
    +---- CPU Renderer
    |
    +---- GPU Renderer
```

CPU Renderer 解释 DrawList，执行原来的软件光栅逻辑。

GPU Renderer 把 DrawList 转换成 GPU 顶点、纹理、Shader 和绘制批次。

统一的是绘制语义，不是底层实现。

## 6.3 逐步迁移

建议保留旧 API：

```moonbit
on_draw(widget, painter, rect)
```

新增可迁移的绘制入口：

```moonbit
on_paint(widget, canvas, rect)
```

这里的 Canvas 应该是统一绘制语义接口，而不是直接暴露 GpuCanvas。

逐步迁移：

1. 矩形、圆角矩形。
2. 图片和纹理。
3. 路径与描边。
4. 渐变。
5. 裁剪、透明度和变换。
6. 文本与字形缓存。
7. 阴影和模糊。

旧控件继续运行。

新控件可以优先使用统一绘制接口。

# 7. 文本渲染策略

不建议第一阶段重写文本排版。

保留：

- Pango。
- DirectWrite。
- macOS CoreText。

CPU 继续处理：

- 字体选择。
- 字形 shaping。
- 行布局。
- 字符位置。
- 光标位置。
- 文本选择。

GPU 负责：

- 字形纹理采样。
- 字体图集缓存。
- 透明度混合。
- 最终合成。

可以逐步引入 Glyph Atlas。

这样既保留现有文本质量，也能减少 CPU 每帧的文本像素绘制工作。

# 8. GPU 资源管理

建议按 WindowHost 管理资源。

GPU 资源包括：

- Surface。
- Device。
- Queue。
- Texture。
- TextureView。
- Sampler。
- Pipeline。
- BindGroup。
- VertexBuffer。
- Glyph Atlas。

建议区分：

1. 进程级 Device / Queue。
2. 窗口级 Surface / Swapchain。
3. 窗口级 Render Target。
4. 后端级资源缓存。
5. 控件级资源引用。

不要让普通 Widget 自己管理 wgpu 原始对象。

GpuCanvas 可以继续作为高级用户的低层 GPU 接口。

# 9. 性能优化方向

不能认为 GPU 一定比 CPU 快。

必须根据真实性能数据决定哪些工作值得迁移。

建议重点观察：

| 指标 | 目的 |
|---|---|
| Layout Time | 布局耗时 |
| CPU Paint Time | CPU 绘制耗时 |
| GPU Upload Bytes | 上传字节数 |
| GPU Submit Time | GPU 命令提交耗时 |
| GPU Render Time | GPU 绘制耗时 |
| Present Time | 窗口呈现耗时 |
| Frame Time | 完整帧耗时 |
| p95 Frame Time | 卡顿情况 |

已有 `NATIVEGUI_PROF` 可以作为基础。

建议扩展上传量、GPU 提交和 GPU 完成时间的读数。

优先优化：

1. 静态控件缓存。
2. 脏区绘制。
3. 脏区纹理上传。
4. DrawCall 合批。
5. 字形缓存。
6. GPU 动画。
7. 大面积图片和复杂图形。

普通 Button、Panel 等控件不一定需要 GPU 专属优化。

# 10. 自动化测试要求

至少建立以下测试。

## 10.1 双后端视觉对拍

同一份 Widget Tree：

- 软件光栅输出图片。
- GPU Renderer 输出图片。
- 对比像素差异。

注意字体抗锯齿和不同 GPU 驱动存在差异，应定义合理容差，而不是要求所有平台绝对逐像素相同。

## 10.2 必测场景

- 矩形和圆角。
- 透明度。
- 裁剪。
- 渐变。
- 图片。
- 文本。
- 路径。
- 混合模式。
- Transform。
- 高 DPI。
- Resize。
- 多窗口。
- 动画。
- 滚动。
- GPU 设备丢失。
- GPU 初始化失败。
- 运行时切换。
- 切换时资源释放。

## 10.3 切换测试

重点验证：

```text
Software
   |
   v
Hardware
   |
   v
Software
   |
   v
Auto
```

每次切换都必须保证：

- 控件状态不变。
- 焦点不丢失。
- 输入法不中断。
- 画面没有残留。
- GPU 资源没有泄漏。
- 不出现黑屏。
- 窗口仍能正常响应事件。

# 11. 推荐实施计划

## P0：运行模式切换

目标：让当前 L1 可以在软件呈现和 GPU 呈现之间切换。

工作：

- 增加 RenderMode。
- 每窗口保存 RenderMode。
- 增加 C 侧 GPU Present 启用开关。
- Software 模式跳过 L1。
- Auto 模式保持当前自动探测。
- GPU 模式输出实际运行状态。
- 切换时强制整窗重绘。

不修改现有控件绘制 API。

## P1：窗口级 Renderer 管理

目标：消除进程级 GPU Sink 的限制。

工作：

- Renderer 移入 WindowHost。
- 每窗口管理 GPU 状态。
- 每窗口管理 GPU 资源。
- 移除普通窗口绘制对全局 Sink 的依赖。
- 多窗口 GPU/CPU 混用。

## P2：统一 DrawList

目标：建立 CPU 和 GPU 共用的绘制语义。

工作：

- DrawList。
- CPU Replay Renderer。
- GPU Renderer。
- 绘制状态和命令排序。
- Clip / Transform / Opacity。
- DrawCall 合批。

旧 Painter 保持兼容。

## P3：普通控件逐步 GPU 化

优先：

- 图片。
- 图表。
- 大量简单图形。
- 动画。
- 视频。
- 复杂视觉特效。

不要为了 GPU 把所有控件重写。

## P4：文字与缓存优化

- 字形纹理。
- Glyph Atlas。
- 静态控件缓存。
- GPU 动画。
- 更细粒度的脏区。

## P5：移动端扩展

待桌面 Renderer 抽象稳定后，再接入：

- iOS Metal Surface。
- Android Surface / Vulkan。
- 移动端生命周期。
- 触摸与手势。
- Safe Area。
- IME。
- Accessibility。

# 12. 最终架构原则

1. 一套 Widget Tree。
2. 一套业务状态系统。
3. 一套布局和事件系统。
4. 一套绘制语义。
5. 多个 Renderer。
6. 独立的 Present Backend。
7. 按窗口管理 Renderer。
8. GPU 不可用必须能够降级。
9. 运行时切换不能丢失 UI 状态。
10. 软件光栅始终保留为兼容实现和正确性参考。

**最终目标不是让所有控件都直接调用 GPU，而是让控件只描述自己要画什么，由框架决定如何高效地画出来。**
