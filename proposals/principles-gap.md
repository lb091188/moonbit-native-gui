# 设计原则落差与补齐方案

三条产品原则对照当前代码的差距清单：每条写现状、为什么要加、怎么加、加了的作用。
已由既有提案或 roadmap 覆盖的不在此重复，文末给对照表；各条拍板后按流程进 roadmap「已规划」。

## 〇、口径

1. **分层分级：高层求快、底层求透。** 高层 API 用预设组件、标准布局与默认主题盖住日常构建；底层留逃生通道，不卡死任何定制可能。
2. **视觉掌控下放。** 框架提供一套优质默认外观，不强加设计哲学；主题可自由覆盖，跟随系统原生主题。
3. **平台抹平。** 生命周期、事件、布局跨平台统一；接口一致的前提下尊重目标桌面差异，配合「诚实降级」。

**评估基准的对齐**：本库是自绘渲染路线（roadmap「明确不做」：原生控件皮肤不作主题化路径），所以「暴露底层原生句柄」不照搬 GTK 字面（GtkWidget 即产品），对齐为：**自绘栈内部原语全量可及（已达成）+ 平台窗口句柄按逃生口径透出（未达成，见 1.1）**。

## 一、分层分级：底层求透

### 1.1 平台原生句柄透出 MoonBit

**现状**：`Window.id` 是内部槽号（1 起，`gui/win/stub.c` 的 `wm_windows[]` 槽表），不是 HWND/XID/NSWindow。唯一交出真句柄的 `wm_surface_container(surface_id) -> GtkWidget*`（stub.c GTK 分支）只在 C 链接层可见，仅供 gui-webview 的 C 桩取父容器；MoonBit 侧没有任何 extern 声明可拿真句柄。

**为什么要加**：开发者面对平台特例（Win32 API 直调、GDK 特性、Cocoa 私有面之外的扩展点）时只能自己另写 C 桩、重复窗口槽表的内部知识。这是「不卡死任何定制可能」唯一的硬缺口：自绘、样式、事件都有逃生口，唯独「借原生窗口做平台特化」没有。

**怎么加**：三平台各一个 `wm_native_handle(int64_t slot) -> int64_t`，返回 HWND / GdkWindow*（或 GtkFixed 容器指针，口径在契约注释钉死）/ NSWindow*；MoonBit 侧 `Window::native_handle() -> Int64`，文档标注「裸句柄、平台语义、仅逃生用，跨平台代码不得依赖」。Windows 分支取槽表里的 hwnd，GTK 分支复用 `wm_surface_container` 的取法，mac 分支取桩内保存的 NSWindow*；无窗口后端的兜底分支回 0。

**加了的作用**：高级用户可经 FFI 直调平台 API 而不必复制库的槽表内部结构；生态扩展（SDL/D3D 内容挂窗、第三方原生控件桥）有了官方入口；gui-webview 那类「C 桩互借句柄」的模式从此可复用。

### 1.2 原生子件登记流程成文

**现状**：`ChildKind` 枚举只登记 `Webview`（`gui/win/surface.mbt`），头注明言「逐条登记，不开放自定义值」。这个保守立场与 roadmap「按平台开关的原生兜底例外需逐条登记评审」一脉相承，本身是对的；缺的是登记流程没有成文，下一类子件要接时无既定通路。

**为什么要加**：白名单不开放是纪律，但每接一类新子件（原生视频面、地图控件、第三方 HWND/GtkWidget 嵌入）都要重新发明「三平台各一套挂载/卸载/geometry 同步」的接入步骤。流程不写下来，这个能力就依赖当事人的记忆。

**怎么加**：在 `gui/win/surface.mbt` 头注（或本文件附一节）写死登记清单：新增 kind 需 ①三平台桩各实现挂载/移除/矩形同步；②能力缺失平台的兜底行为（`None` 返回）；③探针 + 真机用例。第一个照此流程演练的候选是 gui-media 的视频直出面（省一层纹理回读）。

**加了的作用**：原生子件从单点能力变成可复制的接入流程；视频直出有了预铺的路。

### 1.3 grid 布局原语

**现状**：布局面只有 row/col/view（flex 直通 yoga）。无 grid 构造器，表格型布局要用 `flex_wrap` + `width_percent` 手拼，列对齐没有保证。

**为什么要加**：设置页、表单栅格、图片网格是常见形态，手拼有样板噪声且对齐靠手工巧合。高层求快的原则下，这类高频形态该有一行可用的原语。

**怎么加**：`@ui.grid(columns, children, gap?, ...)`，纯 MoonBit 实现，不引入 CSS grid 全语义：先测后布（一遍测子项列宽、一遍按列组装行容器），支持等宽 N 列与显式列宽两档，向上盖住大多数需求。放 `gui/ui/` 布局组，与 row/col 同级。

**加了的作用**：网格布局一行可用，去掉手拼样板；列对齐由布局原语保证。

### 1.4 `@ui` 公共面收窄

**现状**：`button_skin` / `button_skin_token` / `paint_subset` / `fold_color` / `mask_of` 等实现性函数出现在 `gui/ui/pkg.generated.mbti` 公共 API 里。

**为什么要加**：高层包的价值在面窄好用。实现细节一旦 pub，用户误用即成事实稳定面，0.x 之后想收就是破坏性改动；这与 roadmap 已规划的「稳定面清单与 1.0 时点」直接冲突——现在不收，将来划稳定面时收不动。

**怎么加**：逐个判断去向：纯实现细节去 pub（0.x 阶段破坏成本低，破坏记提交信息）；确有外部价值的（如 `fold_style`）保留并写进文档。改动同批核对 examples 与测试文档无引用。

**加了的作用**：公共面变窄，稳定面清单可划；用户面里留下来的都是承诺维护的。

## 二、视觉掌控下放

### 2.1 主题 JSON 配置加载

**现状**：主题覆盖只有 MoonBit 值构造（`Theme` 是 `pub(all)`，字面量或 `theme_from_accent` 派生）；gui/theme 下无任何外部格式解析。

**为什么要加**：应用分发给最终用户后，换肤（品牌色、圆角偏好、深浅预设）必须重新编译。「尊重用户」这条对终端用户不成立。design.md §0「不实现运行时求值」针对的是样式属性名层面；主题 JSON 只承载**固定字段名的值映射**（20 颜色 + 刻度），不引入属性名解析器，与该决策不冲突。

**怎么加**：`@theme.from_json(String) -> Result[Theme, String]`，复用 `@sys` 已有的 JSON 原语读值。字段名白名单 = `Theme` 字段名，未知字段报错（对齐 `check_color` 构造期校验的口径）；允许部分字段缺省（缺省项回落 `default_theme()`/`dark_theme()` 基底）。应用自行决定加载时机与文件来源。

**加了的作用**：主题可随应用分发为数据文件，用户/设计者改主题不碰编译；企业品牌定制不需要 fork。

### 2.2 跟随系统主题默认接线

**现状**：进程初始主题硬编码 `default_theme()`（`gui/theme/theme.mbt`）；`follow_system_theme` 是 opt-in 且靠轮询（默认 1s，指纹防抖，`gui/widget/app.mbt`）。三平台探针本身扎实（注册表 / GSettings 含回退 / NSAppearance）。README 写 "followed by default"，实现是 opt-in——表述强于实现。

**为什么要加**：深色系统首次启动白闪是桌面应用常见差评点；「跟随系统」是多数用户的默认期待，不该要求每个应用记得接线。

**怎么加分两层**：
- **表述对齐（最低成本）**：README 与教程写明当前为 opt-in。
- **行为落实**：`mount_window` 时默认做一次 `theme_from_system` 探测并应用（单次探测无轮询成本），显式 `theme_apply` 的应用不受影响；轮询跟随器保持 opt-in。事件驱动（WM_SETTINGCHANGE / GSettings notify / KVO）不在本条范围——「循环归 MoonBit」架构下要在三平台桩各加监听源，收益/成本不划算，轮询+指纹防抖已够用。

**加了的作用**：README 表述成真；深色系统下首次启动不再白闪。

### 2.3 `dark:` / `light:` 类变体接入组件消费

**现状**：`resolve_with_variant`（`gui/style/class_registry.mbt`）已实现 `dark:`/`light:` 前缀解析，但组件内部零消费，仅测试引用。

**为什么要加**：机制实现了没人用，就会成为第二个 `letter_spacing`（死字段，见 style-css-expansion.md 〇.3）。深浅切换时确有个别样式需要分档（阴影深浅、边框强度、代码视图底色），现在只能运行时 if。

**怎么加**：从 `style/tokens.mbt` 挑 2–3 个确实需要深浅分档的内置样式改用变体前缀写法，让机制有真实消费者；补「切深浅后变体生效 + 重绘」的回归测试。

**加了的作用**：变体机制从「实现了」变「用起来了」；组件深浅适配有了既定写法。

### 2.4 code_view 主题化

**现状**：code_view 整套 One Dark 色板硬编码（`gui/ui/codeview.mbt`），不随主题；docs/zh/components.md 自认。

**为什么要加**：组件矩阵里唯一整块脱离主题的组件——浅色主题下是突兀的深底块，深色定制主题下色板不跟。违背「框架仅提供默认外观，但允许覆盖」的口径。

**怎么加**：色板抽成按 `Theme` 派生的代码配色（深浅基底各一套：背景/前景/关键字/字符串/注释等映射到 theme token 或从 theme 派生），默认跟随 `theme_current()`；保留显式指定代码主题的参数（如 `code_theme="one-dark"`）给刻意场景。

**加了的作用**：组件矩阵视觉一致性补齐；代码块在任意主题下不再是孤岛。

### 2.5 主题定制示例模块恢复

**现状**：`examples/hello-themed`、`examples/design-recipes` 已删（commit 37070e54，目录仅剩空占位）；现存定制示范只有 showcase `apply_theme` 一处片段。

**为什么要加**：「简单直观的主题配置能力」需要可抄的最小起点。现在上手路径断了：文档讲概念，示例看不全，能抄的散在 demo 板里。

**怎么加**：按落位判据建 `examples/theme-playground/` 独立模块注册 `moon.work`，四个最小页：`theme_from_accent` 换主色、`theme_apply` 全量覆盖、`follow_system_theme` 接线、`class` 单组件覆盖。同批补 `测试用例.md` 对应用例。

**加了的作用**：主题定制有可复制的官方起点；文档站示例链接有落点。

## 三、平台抹平

### 3.1 同签名未实现端可探测

**现状**：窗口方法族存在「同签名、悄悄无效」：W20e 窗口增强（改标题/图标/最小尺寸/无边框）非 Windows 端空实现、读回 0/false（`gui/win/window.mbt`）；`set_opacity` 无合成器时静默无效；`set_transparent_bg` Windows 需先无边框的前置不报。而系统能力族是 `*_supported()` 真探测 + `Unsupported`/`Failed` 分档——同一库内两套口径。

**为什么要加**：「诚实降级」是全库纪律（README Highlights 明写），窗口方法族读回假值与之相悖。调用方无法区分「本平台没实现」「当前环境不生效」「调用失败」，跨平台代码会写出看似统一、实际只在单平台生效的逻辑。

**怎么加**：分两步走。第一步（文档）：契约注释逐平台钉死读回值含义（roadmap 窗口节已有 🚧 平台标注，方法注释补齐）。第二步（签名，0.x 阶段做破坏性改动成本最低）：这批方法补 `*_supported()` 探测或 setter 返回 `Result`/`Bool`；「前置不满足」（如 Windows 透明底需先无边框）进 `Failed` 档带原因文案。

**加了的作用**：同签名下的能力差异从「读回假值」变「可探测、可区分」，窗口族对齐系统能力族的诚实降级口径。

## 五、优先级建议

对三条原则达成度影响排序：

1. **1.1 原生句柄透出**——唯一「卡死定制」的硬缺口；
2. **2.1 主题 JSON + 2.2 跟随默认接线**——原则 2 的字面要求与默认体验；
3. **3.1 未实现端可探测**——对齐全库诚实降级纪律；
4. **1.3 grid、1.4 公共面收窄、2.3 变体消费、2.4 code_view**——补齐类；
5. **1.2 登记流程成文、2.5 示例恢复**——低成本随手项，可搭车同批提交。
