# Contributing

中文：[CONTRIBUTING_ZH.md](CONTRIBUTING_ZH.md) · Setup: [docs/build.md](docs/build.md)

In one line: a **cross-platform desktop GUI framework** for MoonBit — one MoonBit codebase ships native windows on Windows / Linux / macOS, self-drawn UI, no heavyweight graphics engine.

## 1. Get it running

```sh
cd gui && moon check --deny-warn          # zero errors, zero warnings
cd examples/hello && moon run .           # minimal window
```

Toolchain install, dev dependencies (GTK3 headers on Linux, MSVC on Windows, Xcode CLT on macOS), the environment self-check and the failure table all live in [build.md](docs/build.md) §1–§4 and §6 — not repeated here.

## 2. Gates (same as CI)

```sh
cd gui
moon check --deny-warn
dbus-run-session -- moon test base shell widget ui render text theme icons sys input win dbus chart mdview style router
```

- **A bare `moon test` is not the library gate**: it also pulls in examples, `experiment/` and the media modules, which carry platform-adaptation gaps that are not library defects. Name the packages explicitly.
- Editing a C stub (`gui/*/*.c`, `*.cpp`) does not necessarily relink: `moon build` may report `no work to do` and reuse the old artefact, so the behaviour looks unchanged. Run `moon clean` after stub edits ([build.md](docs/build.md) §9).
- Toolchain changes also need: `cd tools/native-gui-tools && moon test ./mngkit ./mng ./proc ./inst`.

## 3. Where things go

| Path | Contents |
| ---- | -------- |
| `gui/` | The library, one directory per package (`ui` / `widget` / `style` / `theme` / `render` / `text` / `input` / `win` / `sys` / `dbus` / `shell` …) |
| `gui/<pkg>/stub.c` | Platform C stubs: one file, four conditional arms (Win32 / GTK / macOS / headless fallback); link flags belong to `gui/scripts/prebuild.mbtx` |
| `examples/<name>/` | Each example is its own MoonBit module, registered in the root `moon.work` |
| `modules/` | Sub-modules (yoga-mbt / mdparse / gui-media / gui-webview / ffmpeg-mbt) |
| `experiment/` | Probes and micro-benchmarks, never shipped in the library |
| `tools/` | DX tooling and editor plugins |
| `docs/zh/` + `docs/` | User docs: Chinese first, English mirrored at the same path |
| `测试文档/` | Real-hardware test cases (`测试用例.md` is the single source of truth; the recorder page loads it) |

## 4. Design stance

- **Honest degradation**: if a platform does not implement something, say so — no fake return values, no silent no-ops. Cross-platform contracts are set by the **strictest** platform; extra capabilities of looser platforms stay internal.
- **APIs come from real use cases**: when filing a feature request, lead with the scenario you are stuck on. "Another toolkit has this" is not a reason (see the "Explicitly not doing" list in the [roadmap](docs/zh/roadmap.md)).
- **Appearance is fully overridable**: themes, style slots and named classes are the override points; new components must derive colours from theme tokens instead of hard-coding a palette.
- **Comments state what something is and how to use it**: rationale, root causes and platform pitfalls go to `experience/adaptation/`, committed with the code.
- **Formatting**: follow the surrounding code. Do **not** run `moon fmt` across the repository — it sweeps unrelated files into your diff.

## 5. How testing splits

- **Headless assertions are yours**: logic, state machines, layout numbers and pixel snapshots live in `*_wbtest.mbt` next to the code (white-box, private functions welcome). `moon check --deny-warn` and `moon test` must be clean.
- **Visual and interactive checks are run by a person**: walk the numbered cases in `测试文档/测试用例.md` on all three platforms. Report format: `case id + symptom + screenshot (when possible) + the readout line printed at exit`.
- New user-visible behaviour needs a case entry; library-level criteria without an example entry go to appendix D of that document.
- Example apps must **not** self-exit — the person closes the window.

## 6. Commits and pull requests

- One feature per commit; the message is `【tag】what it does`, e.g. `【样式】background gradient wired into view boxes`.
- Breaking changes are allowed during 0.x but must be named in the commit message and docs, with the blast radius and the migration. `pkg.generated.mbti` is generated by `moon info` — do not hand-edit it.
- Fill in the PR template: gate readouts, whether each of the three platforms was actually run (write "unverified" rather than leaving it blank), and which docs were updated.
- Start from current code: `git fetch && git rebase origin/master`.

## 7. Asking

Use the [issue templates](.github/ISSUE_TEMPLATE): bug reports need platform, versions, steps and the exit readout; feature requests need the real use case and the per-platform API channel.
